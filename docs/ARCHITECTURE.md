# DayMate: концепция, архитектура и план

## 1. Анализ идеи

Сильная сторона — один список дня вместо четырёх приложений (таблетки, задачи, календарь, привычки).
Главный риск — доверие к напоминаниям о лекарствах: если приложение хоть раз «тихо» пропустит приём
или само отметит его принятым, им перестанут пользоваться. Поэтому в основе три правила:

1. «Принято» появляется только после действия пользователя. Наступившее время даёт статус «Пора принять»,
   прошедший день без ответа — «Нет отметки».
2. Приложение честно сообщает о своих ограничениях: веб-версия не может напоминать при закрытом браузере,
   и это написано в настройках, а опоздавшее напоминание помечается как опоздавшее.
3. Данные о здоровье не покидают устройство без явного решения пользователя.

## 2. Улучшения, добавленные к исходному описанию

| Улучшение | Зачем |
|---|---|
| Приостановка лекарства вместо удаления | Курс прервали — история остаётся |
| Статус «Нет отметки» отдельно от «Пропущено» | «Забыл отметить» и «решил не принимать» — разные вещи |
| «Только это событие / вся серия» при правке и удалении | Иначе перенос одной пары ломает всё расписание |
| Отмена удаления в течение нескольких секунд | Меньше страха нажать не туда |
| Цель «N раз в день» у привычки | Вода — это 8 стаканов, а не одна галочка |
| Правка привычек задним числом | Отметить вчерашнее вечером следующего дня |
| Предупреждение о смене часового пояса | В поездке расписание лекарств требует внимания |
| Проверка файла при импорте, копия повреждённых данных | Сбой не уничтожает данные молча |

Расписание вуза построено на тех же событиях: занятие — это `PlannerEvent` с `kind: 'class'`, аудиторией и преподавателем.
Отмена одной пары — статус `cancelled` у экземпляра: напоминание не приходит, в статистику пара не входит.
Напоминания о занятиях не повторяются и не используют громкий канал.

Сознательно не сделано: подсказки по дозировкам, совместимости и «что делать при пропуске» — это зона врача.

## 3. Состав первой версии (MVP)

Готово в этапе 1: шесть страниц, локальное хранение, повторения, напоминания в браузере, тёмная тема,
экспорт / импорт, адаптивная вёрстка (нижняя панель на телефоне, боковая на компьютере), тесты логики.

## 4. Структура проекта

```
src/
  models/types.ts          модели данных (единственный источник типов)
  lib/                     утилиты: даты, идентификаторы, цвета категорий
  domain/                  чистая логика без React и без хранилища
    schedule.ts              повторения: occursOn()
    agenda.ts                дела дня, статусы приёмов
    habits.ts                серии и периодичность
    stats.ts                 статистика за период
  storage/
    adapter.ts               интерфейс StorageAdapter + реализация на localStorage
    schema.ts                версия схемы, значения по умолчанию, проверка данных
  store/
    mutations.ts             чистые функции изменения данных
    AppStore.tsx             состояние приложения и сохранение
  reminders/
    plan.ts                  какие напоминания есть и какие пора показать (чистая логика)
    notifier.ts              системные уведомления браузера
    nativeSchedule.ts        что передать планировщику Android (чистая логика)
    native.ts                вызовы плагина уведомлений Android
    ReminderProvider.tsx     тик, пробуждение вкладки, действия пользователя
  components/              ui/, layout/, events/, medications/, habits/
  pages/                   шесть страниц
  __tests__/               тесты domain/, reminders/, storage/
public/sw.js               service worker: кнопки и клики в уведомлениях (веб)
android/                   Android-оболочка (Capacitor); каналы уведомлений — в MainActivity.java
```

Зависимости направлены в одну сторону: `pages → components → store / reminders → domain → models`.
`domain/` и `store/mutations.ts` не знают про React, поэтому переносятся в мобильное приложение и на сервер без изменений.

## 5. Модель времени

- Дата хранится как локальный календарный день `YYYY-MM-DD`, время — как время на часах `HH:MM`.
  Это семантика будильника: «09:00» остаётся 09:00 в любом поясе и при переводе часов.
- Моменты действий пользователя («принял в…», «отложено до…») хранятся в UTC (ISO).
- Разница дней считается по календарю, а не по миллисекундам, поэтому переход на летнее время не сдвигает серии.
- При запуске сравнивается часовой пояс устройства с сохранённым; при смене показывается предупреждение.

## 6. Напоминания

### Как работает сейчас (браузер)

1. `planReminders()` строит из данных список неподтверждённых напоминаний за вчера–завтра.
2. Каждые 15 секунд, а также при возврате во вкладку `decideDeliveries()` сравнивает план
   с **текущим временем на часах** и журналом доставки в localStorage.
3. Сработавшее напоминание показывается внутри приложения всегда, системным уведомлением — если разрешено.
4. Без ответа оно повторяется с заданным интервалом заданное число раз. «Отложить» задаёт новое время срабатывания.

Почему не `setTimeout` на нужное время: такие таймеры теряются при перезагрузке, замедляются в фоновых вкладках
и ломаются при переводе системных часов. Сверка с часами и журналом этих проблем не имеет: после перезагрузки
нет дублей, после «сна» вкладки пропущенное показывается сразу и помечается как опоздавшее.

Ограничение, которое нельзя обойти в браузере: при закрытой вкладке код не выполняется, уведомление не придёт.

### Как работает в Android-приложении (сделано)

Оболочка Capacitor + плагин `@capacitor/local-notifications`. Исполнитель плана — не тик в браузере, а планировщик Android.

1. `nativeSchedule.ts` (чистая логика) строит из плана список на 14 дней: для каждого неподтверждённого напоминания —
   первое уведомление и повторы через `repeatMinutes` (по умолчанию 10 минут, до 3 повторов).
2. `native.ts` при каждом изменении данных и при открытии приложения отменяет старые будильники и передаёт системе новые
   (`setExactAndAllowWhileIdle`). После перезагрузки телефона плагин восстанавливает их сам.
3. Ответ пользователя («Принял», «Отложить», «Пропустить» — в приложении или кнопкой в уведомлении) убирает напоминание
   из плана, поэтому оставшиеся повторы отменяются.
4. «Громче» сделано вторым каналом уведомлений (`MainActivity.java`): в Android звук задаётся каналом, а не отдельным
   уведомлением. Канал повторов использует длинный сигнал, усиленную вибрацию и аудиопоток будильника.

Ограничения: расписание покрывает 14 дней и не более 300 ближайших уведомлений; кнопка в уведомлении открывает приложение,
чтобы записать ответ; производители с агрессивной экономией батареи могут задерживать уведомления.

### Варианты фоновых уведомлений

| Вариант | Как работает | Когда подходит |
|---|---|---|
| **Локальные уведомления ОС** (рекомендуется для лекарств) | Мобильное приложение (Capacitor или React Native) заранее передаёт ОС расписание на 2–4 недели вперёд: Android `AlarmManager.setExactAndAllowWhileIdle`, iOS `UNCalendarNotificationTrigger`. Срабатывает без сети и без запущенного приложения | Основной механизм |
| **Push с сервера** | Сервер хранит расписание и отправляет push через FCM / APNs (в вебе — Web Push) | Синхронизация устройств, семейные напоминания |
| **PWA + Web Push** | Установленная веб-версия получает push от сервера | Быстрый промежуточный шаг без магазинов приложений |

Что учесть в мобильной версии:

- Android 12+: разрешение на точные будильники; Android 13+: разрешение на уведомления; перепланирование после
  перезагрузки телефона (`BOOT_COMPLETED`) и после смены времени или пояса (`TIME_SET`, `TIMEZONE_CHANGED`).
- Производители с агрессивной экономией батареи: экран с инструкцией, как исключить DayMate из оптимизации.
- iOS: не более 64 запланированных уведомлений — планировать ближайшие и пополнять очередь при каждом запуске.
- Кнопки «Принял / Отложить» прямо в уведомлении записывают действие без открытия приложения.
- Повтор без ответа: планировать цепочку из нескольких уведомлений и отменять остаток при подтверждении.

Перенос прост: `plan.ts` уже выдаёт список «что и когда», меняется только исполнитель — вместо тика в браузере
планировщик ОС. Для этого `notifier.ts` получает второй вариант реализации.

## 7. Готовность к расширению

| Планируемая функция | На что опирается |
|---|---|
| База данных, облако, авторизация | `StorageAdapter` асинхронный: добавляется новый адаптер, выбор — одна строка в `main.tsx` |
| Синхронизация устройств | У записей есть `id`, `createdAt`, `updatedAt`; изменения проходят через `mutations.ts` — там же появится журнал изменений |
| ИИ-ассистент, голосовой ввод | Результат разбора фразы — обычный объект `PlannerEvent` / `Medication`, сохраняемый теми же мутациями после подтверждения пользователем |
| Мобильное приложение, виджеты | `domain/`, `store/mutations.ts`, `reminders/plan.ts` не зависят от браузера |
| Семейные напоминания | Потребуют сервера и явного согласия; поле владельца добавляется миграцией схемы (`schemaVersion`) |

## 8. Безопасность и приватность

- Никаких сетевых запросов, аналитики и внешних шрифтов: приложение работает полностью локально.
- Собирается минимум: имя нужно только для приветствия и необязательно.
- Пользователь управляет данными: экспорт, импорт, полное удаление.
- Известное ограничение: localStorage не шифруется. Для облачной версии — шифрование при передаче и хранении,
  отдельное согласие на обработку данных о здоровье, проверка требований закона о персональных данных.

## 9. План следующих этапов

1. **Этап 2 — доводка веб-версии:** установка как PWA и работа офлайн, перенос на IndexedDB, напоминания для привычек,
   поиск, недельный вид календаря, тесты интерфейса.
2. **Этап 3 — мобильное приложение:** Android сделан (оболочка Capacitor, уведомления ОС, громкий повтор); дальше — подпись и публикация, своя иконка, iOS.
3. **Этап 4 — аккаунт и облако:** авторизация, синхронизация, push с сервера.
4. **Этап 5 — ассистент:** создание напоминаний текстом и голосом, виджеты, семейный доступ.
